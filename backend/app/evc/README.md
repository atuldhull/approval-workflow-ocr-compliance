# evc (Person 1)

Implemented storage:
- `evc_request`, `expert`, `availability`, `coi`, `slot`, `assignment`, `schedule_run` tables (schema `evc`), plus trigger-owned `assignment_expert` membership rows.
- Independent `evc_0001` Alembic chain, branch label `evc`; dependency on stable `wf_0001` application/institution IDs only.
- `assignment.expert_ids` is the requested UUID array. PostgreSQL mirrors all members, including proposals, to `assignment_expert`, validates expert references, and uniquely reserves `(expert_id, date, slot_part)` only while published. Inserts, publication, expert/slot changes and trigger-synchronized slot calendar edits all enforce the same constraint. Every FK references a stable UUID ID only; mutable dates/parts are synchronized under slot SHARE locks rather than FK targets. Direct membership INSERT/UPDATE/DELETE is rejected; application code writes assignment only.
- `schedule_run.parameters` and `metrics` are objects with recursively numeric/boolean/null values, arrays and coded keys. String values/free text are rejected in the database. Algorithm is a separate EDF/CPSAT column; run status and panel roles are uppercase coded tokens, without an invented approval lifecycle.
- No personal information: experts contain only opaque user_ref, region, coded expertise tags and active flag. No published P3 user table exists, so user_ref has no invented FK; EVC/wf links target stable IDs.

The EVC seed writes only evc: 30 fictional DEMO expert references in nine DEMO_REGION_nn regions (the benchmark pool), 3600 AM/PM availability rows across 60 logical dates, and 3 DEMO COIs referencing the three existing fictional institutions; plus six DEMO experts in each region the seeded institutions use (Northern, Southern, Western) with 60 days of availability and no COIs, so the demo's own cases can be proposed and published (48 experts, 5760 availability rows in all). The supplied ClockPort is the only date source. UUID5 IDs and availability patterns are deterministic; repeat runs preserve identical rows and conflicting curated rows are refused. The CLI requires DEMO_MODE=true and the seed transaction rolls back on missing referenced institutions or conflicting rows. Seed data never belongs in migrations and no real user accounts are created. See docs/p1/ASSUMPTIONS.md and docs/p1/plans/3.1_evc_schema.md.

Implemented queue/lifecycle:
- `GET /api/evc/queue` filters region/status and inclusive due_by date bounds (`from`, `to`), with offset/limit pagination and stable ordering. Institutions see only their own cases; ROs only their region. Scope comes from CasePort/AuthzPort before totals and pagination.
- Actual workflow EVC entry (including generic advance and deficiency review) calls the public EvcPort, creates one request per source visit and one live clock, and emits evc.request_created.v1 inside the same unit of work. Duplicate/replayed commands cannot create a second clock. Later authorized re-entry gets a distinct historical request.
- complete_evc and normal EVC exits close MET and mark DONE with evc.request_completed.v1. Last-applicable EVC (SHC skipped) has a guarded completion self-transition; no route's stage list changes. Unscheduled reject/withdraw/revert exits cancel/close WAIVED with evc.request_cancelled.v1. Scheduled cancellation fails closed until an assignment-unpublication lifecycle exists.
- evc_0002 adds pinned rule/ruleset/deadline/visit references and closed_at, keeping legacy rows nullable rather than fabricating provenance. Legacy duplicates make the active uniqueness migration fail explicitly; existing cached ruleset checksums remain immutable. Use a fresh disposable demo database for the approved r1 source changes.
- EVC_PROCESSING is an INTERNAL/COMMITTEE clock with a configurable **7 calendar-day DEMO ASSUMPTION**, not an APH-confirmed duration. Queue rows expose source_status, assumption_code, duration_days and pinned metadata. Waiting days count elapsed 24-hour periods and stop at completion/cancellation. P2 alone owns overdue escalation; P1 only opens/closes through DeadlinePort.

Expert pool management:
- `POST /api/evc/experts` accepts opaque P3 user_ref, coded region/tags, active and optional personal_details. Contact fields go exclusively through PersonalDataPort; expert/event/response data retains only personal_ref. Identity is explicitly P3_USER_REF_UNVERIFIED until P3 supplies an authoritative lookup interface. Duplicate user_ref returns 409.
- `POST /api/evc/experts/{id}/availability` atomically sets `items: [{date, slot_part, available}]` (1–732 unique keys); identical repeats produce no new events. `POST /api/evc/coi` records matching INSTITUTION_LINK, PRIOR_ENGAGEMENT or RECUSAL source/reason codes; duplicates are no-ops.
- `GET /api/evc/experts?region=&available_on=` is a scoped directory, with optional slot_part and offset/limit. Date filtering excludes inactive, missing/false availability and reserved experts. RO users only manage/read their own region. It has no institution context; COI filtering belongs to request-specific eligibility.
- `eligibility.eligible_experts(request, date, slot_part)` consumes an immutable EligibilityRequest snapshot, returns UUID-sorted ExpertCandidates and performs no I/O/clock access. `pool.eligibility_snapshot(session, request_id)` loads own EVC tables and the pinned RulesetPort policy; a future scheduler must recheck before reserving/publishing. All COIs exclude; both proposed/published assignments reserve that date/part conservatively. YAML SAME_REGION/ANY_REGION/OTHER_REGION policy and AM/PM codes are labelled DEMO ASSUMPTION.
- Lifecycle audit events: evc.expert_registered.v1, evc.availability_set.v1, evc.coi_recorded.v1. evc_0003 adds nullable opaque personal_ref only; no user master copy or personal fields in evc.

SIMULATED authorised selector (stand-in):
- `selector.select_panel(request, date, slot_part)` is a pure deterministic selector over immutable eligibility, policy and assignment facts. It returns exactly the configured N experts or INSUFFICIENT_CANDIDATES with an empty panel. No appointment, database write or reservation occurs.
- Hard eligibility is reused before ranking. Minimum expertise matching and panel size come from the pinned `expert_pool.selector` YAML policy. Lexicographic ranking is distinct expertise matches descending, assignment workload ascending, oldest earlier assignment date (none first), then UUID ascending. Workload includes proposed/published and future commitments; rotation excludes same-day/future dates. All scored criteria and matched tags are machine-readable in the result.
- `selector_service.selector_request(session, request_id)` loads the request's pinned policy and all EVC assignment history; the future scheduler must authorize and recheck/reserve at publication. `GET /api/evc/requests/{id}/panel-preview?date=YYYY-MM-DD&slot_part=AM` exposes a read-only labelled preview to existing pool readers with case scope. RO readers require their own case and SAME_REGION policy; global readers can preview cross-region policy. Only QUEUED/PROPOSED requests are previewable.
- Code, API and documentation use the exact label **SIMULATED authorised selector (stand-in)**. Size 3, DEMO expertise tag, minimum 1 match and the ordered criteria are DEMO ASSUMPTION, not an official APH selection policy. P3 identity lookup is still absent; responses retain P3_USER_REF_UNVERIFIED. See docs/p1/selector_report.md for the controlled 100-request comparison and limitations.

EDF baseline and shared metrics:
- `scheduler_edf.plan_edf(problem)` is pure: queue order `(due_by, requested_at, UUID)`, slot order `(date, AM/PM, UUID)`, first feasible complete panel through select_panel, with capacity and expert reservations updated between requests. No random source or wall-clock. Proposed/published reservations count conservatively.
- `scheduler_edf.propose_edf(principal, ScheduleCommand(run_id, horizon_start, horizon_end, region=None))` wraps `handle(uow, command)` in one transaction. Dedicated authorization comes first; scheduling/request/slot/expert locks protect refreshed input. Persisted results are EDF/PROPOSED runs, unpublished DEMO_PANEL assignments and PROPOSED requests, with atomic evc.schedule_proposed.v1 and evc.assignment_proposed.v1 events. A repeated run ID conflicts; a failure rolls back all effects. Unscheduled requests remain QUEUED.
- `metrics.evaluate_schedule(problem, allocations)` and `metrics.compare_plans(problem, plans)` are shared with future CP-SAT. Metrics include cardinality, lateness vector/total/max, late count, waiting and hard violations. Comparison rejects mixed input fingerprints or incorrect self-reported metrics. Capture the common immutable problem before either algorithm consumes capacity.
- Pinned `expert_pool.scheduler` labels capacity as panels and soft lateness as DEMO ASSUMPTION. An explicit EVC-local planning_until can extend the selector horizon; original due_by/pins/P2 clocks stay unchanged. Existing preview behavior is unchanged. No new table/migration; numeric-only run parameters/metrics remain enforced. See docs/p1/edf_report.md.
- Lifecycle QUEUED → PROPOSED → PUBLISHED → DONE. `EvcPort.status` returns PUBLISHED once published; both complete_evc transitions require it (`evc_schedule_published`: EVC_SCHEDULE_NOT_PUBLISHED before publication, plan 4.1). Cancelling a QUEUED/PROPOSED request withdraws its unpublished drafts; a published assignment still fails closed.

CP-SAT and publication (3.6, on top of the EDF baseline):
- `scheduler_cpsat.solve_cpsat(problem)` / `plan_cpsat(problem)` take the same immutable SchedulingProblem as plan_edf and return a `SchedulingPlan("CPSAT", ...)` scored by `metrics.evaluate_schedule`, so `compare_plans` applies unchanged. CP-SAT chooses a slot per request only: one boolean per (request, slot) the selector can fill against existing reservations (the request's earliest `cpsat_candidate_slots` feasible slots, pinned in `expert_pool.scheduler`, default 12, plus EDF's own), per-expert variables purely as a feasibility witness (exact panel size, one booking per expert per date/part across slots, at most the pinned daily cap of visits per expert per date, slot capacity in panels). Objective, lexicographic through computed weights, follows the shared comparison key: scheduled count, then total lateness, maximum lateness and waiting. The selector forms the real panels through `selector_at` in slot order; an unfillable choice is forbidden and re-solved (up to 5 rounds). The EDF plan is the solution hint and is kept, reported as `fallback_to_edf`, if it ever scores better. Deterministic: one worker, seed 7, deterministic limit 2.0, 60 s wall-clock safety cap. Solver facts are stored numerically in `schedule_run.parameters` (`cpsat_*`, including `cpsat_candidate_slots`).
- Expert daily cap (decided 28 Oct 2026, DEMO ASSUMPTION): pinned `expert_pool.scheduler.expert_daily_cap`, default 1 visit per expert per date, carried as `SchedulingProblem.expert_daily_cap`. `selector_at` treats an expert at the cap as reserved for the rest of that date, so EDF, CP-SAT's witnesses/materialisation and the selector all see the same rule; CP-SAT adds a per-expert per-date constraint; `evaluate_schedule` counts visits beyond the cap as `EXPERT_DAILY_CAP` (earlier commitments are the baseline). A run uses the strictest cap among its requests' pinned rulesets; it is stored as `expert_daily_cap` in the run parameters and returned by propose. Both `expert_daily_cap` and `cpsat_candidate_slots` are optional in the YAML (defaults 1 and 12).
- `scheduler_edf.handle` is the single propose command. `ScheduleCommand` gains `algorithm` (EDF default, or CPSAT) and an optional `slot_capacity` (DEMO ASSUMPTION) that creates canonical AM/PM slot rows only for date/parts in the horizon that have none; existing slot rows keep their capacity. This is the demo path for slots; there is no separate slot endpoint. Both algorithms persist the same way: an EDF or CPSAT PROPOSED run, unpublished DEMO_PANEL assignments, PROPOSED requests, evc.schedule_proposed.v1 and evc.assignment_proposed.v1. The RO region check runs before the platform policy check, which then receives the officer's own region spelling (resource kind `evc`).
- `POST /api/evc/schedule:propose` {run_id, algorithm EDF|CPSAT (default EDF), horizon_start, horizon_end (under 120 days), region?, slot_capacity?} → 201 with metrics, input fingerprint, `expert_daily_cap`, proposals, unscheduled requests and, for CP-SAT, solver facts (including `candidate_slots`). Every unscheduled request keeps `reason_code` NO_FEASIBLE_SLOT (the umbrella) and adds `explanation_code` from `explanations.explain_unscheduled`: NO_AVAILABILITY, PANEL_INCOMPLETE, COI_ONLY, CAPACITY_EXHAUSTED (slot capacity or expert time taken by other visits), EXPERT_DAILY_CAP, or NO_FEASIBLE_SLOT as fallback. Explanations are in the response only; event payloads are unchanged. RO_OFFICER (own region), BUREAU_OFFICER, BUREAU_HEAD. Regions match case-insensitively; an RO naming another region is 403 SCHEDULE_REGION_FORBIDDEN, and a bureau region that no expert or EVC request names is 422 SCHEDULE_REGION_UNKNOWN. A reused run_id is 409 SCHEDULE_RUN_ALREADY_EXISTS.
- `POST /api/evc/schedule:publish` {run_id} → 200. BUREAU_OFFICER/BUREAU_HEAD (`evc.schedule.publish`). Locks run, slots and requests; every request must still be PROPOSED. Rechecks with `evaluate_schedule` against published commitments of other runs: double booking → 409 EVC_EXPERT_DOUBLE_BOOKED, slot capacity → 409 EVC_SLOT_CAPACITY_EXHAUSTED, a visit beyond the daily cap (alone) → 409 EVC_EXPERT_DAILY_CAP_EXCEEDED, any other violation (availability, activity, COI, region, expertise, panel size, window) → 409 EVC_PUBLISH_RECHECK_FAILED. All drafts are published in one statement; the published-only unique index stays the final guard. Requests and the run become PUBLISHED with one evc.assignment_published.v1 per assignment on the application aggregate. Both endpoints accept an optional Idempotency-Key.
- `POST /api/evc/schedule:discard` {run_id} → 200. BUREAU_OFFICER/BUREAU_HEAD (reuses `evc.schedule.publish`, no policy change). Withdraws an unpublished PROPOSED run so its requests can be re-planned: drafts are deleted, their requests return to QUEUED and the run becomes DISCARDED, with one evc.schedule_discarded.v1 on the run aggregate (awaiting three-way approval, docs/p1/contract_requests/2026-10-28_evc_discard.md). A published, discarded or unknown run is 409 EVC_RUN_NOT_DISCARDABLE / 404 EVC_RUN_NOT_FOUND. Optional Idempotency-Key.
- Reading runs back (plan 4.5): propose stores the run's upper-cased `region_scope` (an RO's own region; NULL for a bureau run over every region) and one `evc.schedule_run_request` row per considered request (PROPOSED, or UNSCHEDULED with its explanation code), migration evc_0004. `GET /api/evc/schedule/runs?status=&algorithm=&region=&offset=&limit=` lists runs newest first; `GET /api/evc/schedule/runs/{run_id}` returns parameters (daily cap, slot capacity, candidate window), metrics, solver facts, held assignments with `published`, unscheduled requests with `explanation_code`, and for a discarded run the withdrawn requests. Readers hold `evc.expert.read`; an RO sees only runs planned for their own region (all-region runs are bureau/oversight reading). Runs from before evc_0004 report `outcomes_recorded: false`.
- Per case: `GET /api/applications/{id}/evc` lists the case's requests newest first with the published visit only (date, AM/PM, expert references), scoped like the case. The queue accepts `application_id`.
- Benchmark: `python generator/cases/evc_benchmark.py` (pure, seeded DEMO pool, one shared problem per scenario). Results with the daily cap in docs/p1/plans/3.7_evc_scheduling_decisions.md (3.6 has the uncapped figures).
