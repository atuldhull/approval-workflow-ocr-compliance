1. How the split works

The system is one FastAPI + PostgreSQL modular monolith (§17). The split follows module boundaries, not
technical layers. Each person owns:

        a set of backend folders;
        a PostgreSQL schema, which no one else writes to;
        the API endpoints for their domain;
        the events their module writes to the ledger;
        the tests proving their acceptance criteria.

The one exception is the frontend. P3 builds every screen, and P1 and P2 supply the API and a wireframe or
acceptance test for each screen in their domain. One person owning the UI keeps the look, routing and auth

2. The three rules that prevent conflicts

Rule 1: one writer per table. Each table belongs to exactly one person's PostgreSQL schema ( wf , evc , doc ,
cmp , dl , plat , an ). Code only writes its own schema. To change someone else's data, call their port function
(section 6), never an UPDATE on their table. Reads across schemas go through read-only views that the owner
publishes.

Rule 2: one owner per folder. The folder-to-person table is in docs/OWNERSHIP.md , and it uses only "Person
1/2/3". CODEOWNERS lists all three GitHub usernames for every path, so GitHub asks the team for review without
naming who owns which part. Folder ownership is therefore a written team rule: change someone else's folder
only with their agreement. contracts/ needs approval from all three. CODEOWNERS accepts any one owner's
approval, so a separate CI check ( contracts-approval ) enforces the three-way approval.

 Rule 3: no shared migration head. Each module keeps its own Alembic chain in
  backend/migrations/versions/<module>/ with its own branch_labels , so three people never edit the same
 revision file. Upgrade with alembic -c backend/alembic.ini upgrade heads (plural).
  scripts/check_migration_heads.py runs in CI and fails if any module accidentally grows a second head. Cross-
 schema foreign keys are allowed only to the stable id of a table owned by someone else, and that owner
 promises never to rename or drop it.

 Rule 4: one command, one transaction. A workflow transition, the deadlines it opens, its ledger events and
 any outbox rows commit atomically in PostgreSQL ( unit_of_work ). There is no asynchronous event processing
 for mandatory work such as creating a deadline. Only notification delivery happens later: Person 3's notifier
 reads the outbox after commit.

 Supporting habits:

          Event names carry the module prefix: wf.* , evc.* , doc.* , cmp.* , dl.* , plat.* . Two people therefore
          cannot invent the same event name.
          Stubs first. Every port has a fake in contracts/fakes.py , so nobody waits on anyone.
          Person branches, frequent integration. Each person works on their own person-N branch. Branches are
          integrated into main every 2­3 days (section 14).
          Lightweight local setup. docker compose up runs only Postgres, the backend and the frontend. Heavier
          services (Keycloak, Cerbos, ClamAV, MinIO) come later under an optional profile.
          A 15-minute daily sync covers only what is blocked and which contract needs to change.

6. Interfaces between people (the contracts)

These are the signatures now in contracts/ports.py . A port is a Python call inside the same process and the
same database transaction, not HTTP. This keeps "transition + deadlines + ledger" atomic. Each module
registers its implementations in its own wiring.py , and callers look them up with port(PortType) .

# contracts/ports.py (all three approve changes)

class UnitOfWork(Protocol):                     # P3 - one transaction per command
      session: Session
      principal: Principal

# ---- provided by P3 (platform) ----

class LedgerPort(Protocol):

def append(self, uow, event: EventIn) -> int: ...             # returns seq; schema-checked, hash-chaine

def verify(self, session) -> VerifyResult: ...

class NotesPort(Protocol):

def create(self, uow, body: str) -> tuple[UUID, str]: ... # (note_ref, note_hash)

class PersonalDataPort(Protocol):

def store(self, uow, data: dict, purpose: str) -> UUID: ...

class OutboxPort(Protocol):

def enqueue(self, uow, msg: OutboundMessage) -> None: ...

class AuthzPort(Protocol):

def check(self, principal, action: str, resource: ResourceRef) -> None: ...

# ---- provided by P1 (workflow / intake) ----

class RulesetPort(Protocol):

def default_key(self) -> str: ...                             # "aph-2024-27@r1"

def get(self, key: str) -> RuleSet: ...                       # routes + parsed deadline rules

def route_for(self, category: str, key: str) -> Route: ...

class CasePort(Protocol):

def lookup(self, session, application_id: UUID) -> CaseRef: ... # institution + region, for access c

# ---- provided by P2 (deadlines / compliance) ----

class DeadlineRuleParserPort(Protocol):

main          always runs; changed only by integration

Every day:

git switch person-2                    # your own branch

# ...code...

python -m pytest               # must pass before you push

git add -A

git commit -m "Add escalation ladder"

git push

Every 2­3 days: integration.

     1. All three person branches are merged into a short-lived integration/YYYY-MM-DD branch, in this order:
                 contracts/ ;
                 Person 3's platform;
                 Persons 1 and 2.

     2. Conflicts are resolved and every check runs: tests, the contract check, migration heads, and a frontend
        build.

     3. Anything a person changed outside their own folders is flagged and discussed before merging.
     4. A pull request goes to main . Another team member approves it, and it merges.

Right after each integration, everyone syncs:

git switch person-1
git pull origin main

 Why integrate every 2­3 days and not only at the end:
          Two branches can merge without a conflict and still break the app, for example a function called in one
          shape and written in another.
          Small integrations catch this early, while the change is still fresh.
          Months of divergence surface only in demo week.

 Commit messages: short, imperative, about the change ( Add deficiency loop transitions , Fix month-end
 clamp ).
