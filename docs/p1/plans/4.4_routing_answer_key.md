# Routing answer key plan

Read backend/app/analytics/scorecard.py (`_routing` reads `routing.json` from `ANSWER_KEYS_DIR`, default `generator/answer_keys`, and compares `expected_stages` with the default ruleset's route stage names), test_analytics.py, docs/p1/expected_routes.csv and the Route acceptance assumptions.

## Implementation

`generator/cases/routing_answer_key.py` transcribes the frozen CSV — never routes.yaml — into `generator/answer_keys/routing.json`: one case per route_id with `expected_stages` (an "as applicable" `SHC?` becomes `SHC`, also listed in `as_applicable_stages`), evc, source_table, source_verification and assumption_ref, plus top-level `source` (frozen CSV transcribed from APH Table 2.3 and Chapter I), `source_status` DEMO_ASSUMPTION, `source_verification` PRIMARY_SOURCE_UNAVAILABLE, `assumption_ref` ACCEPTANCE_SOURCE_UNVERIFIED and the CSV's SHA-256. `--check` fails when the JSON is stale. The scorecard ignores the extra fields.

## Tests

`backend/tests/test_routing_answer_key.py`: the committed JSON equals the CSV transcription and is labelled unverified; with the default ANSWER_KEYS_DIR the scorecard's routing line is EVALUATED_ON_ANSWER_KEY with 22/22 correct and PASS.

## Limits

The scorecard compares stage names only, so it cannot tell "always" from "as applicable"; the acceptance tests check that. Agreement is with the project's own transcription: 0/22 rows are verified against the original handbook.
