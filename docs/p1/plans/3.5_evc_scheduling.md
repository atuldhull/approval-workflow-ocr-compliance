## Implementation

1. `scheduler.py` is pure (no database, clock, random source or mutation). It consumes the existing immutable EligibilityRequest/SelectorRequest snapshots and returns proposals, coded explanations and numeric metrics. Optimisation chooses **dates and AM/PM parts only**; every panel is the selector stand-in's exact-N result for that date/part under the commitments made so far. Expert capacity is enforced by feeding full expert-days to the selector as reservations, so the selector itself never sees an over-committed expert.
2. EDF baseline: requests ordered by due_by, priority_key, UUID; each takes its earliest slot in [earliest_date, due_by + max_lateness_days] where the slot has capacity and the selector fills a panel.
3. CP-SAT: one boolean per (request, date, part) that the selector can fill with published commitments only, plus per-expert feasibility witnesses (exact panel size, at most one visit per expert per date/part, expert daily capacity, slot capacity). The witness proves a panel can exist; it is never used as the panel. Objective is lexicographic through computed weights: maximise scheduled visits, then minimise total lateness, then minimise start offset. The EDF plan is the solution hint. After solving, the selector forms real panels in date order (most constrained first within a slot); a slot where it cannot is forbidden and the model re-solved, up to max_repair_rounds. If the result were ever worse than EDF (count, then lateness), the EDF plan is kept and `fallback_to_edf` is reported, so CP-SAT is never below the baseline.
4. Determinism: one worker, fixed seed 7, `max_deterministic_time` 2.0 as the effective limit and a 60 s wall-clock cap only as a safety stop. No wall-clock reading is stored; runtime is measured only by the benchmark script.
5. Explanations: every candidate slot of an unscheduled request is classified by relaxing constraints — no qualified expert at all (NO_AVAILABILITY), fewer than N qualified even ignoring COI and commitments (PANEL_INCOMPLETE), enough only if COIs were ignored (COI_ONLY), or enough but taken by published commitments, capacity or other requests in the run (CAPACITY_EXHAUSTED). The request reports the closest-to-feasible slot reason plus per-reason slot counts, slots considered and best qualified count. Inactive and unavailable experts never count as qualified.
6. `schedule_service.propose` (one unit of work): authorize `evc.schedule.propose` on kind `evc`; RO scope is the principal's own region (body region compared case-insensitively, foreign region 403); bureau may name a region or none. Requests QUEUED/PROPOSED are locked, case scope rechecked through CasePort/AuthzPort (`case.timeline`), and pinned rulesets/selector policies loaded. Live drafts of other requests and all published memberships reserve time, consistent with conservative eligibility; drafts of the requests being rescheduled are superseded (deleted; a run left empty becomes SUPERSEDED). One canonical slot row per date/part (UUID5) carries capacity; missing rows are created with default_slot_capacity. The run records numeric-only parameters/metrics (DB check), proposals are unpublished assignments with panel_role EVC_PANEL, requests become PROPOSED or return to QUEUED, and `evc.schedule_proposed` is appended. A transaction advisory lock serializes proposal runs.
7. `schedule_service.publish` (one unit of work): authorize `evc.schedule.publish` (bureau only). Lock the run, its slot rows and requests. The run must be PROPOSED with drafts; each request must still be PROPOSED. Recheck with published commitments only: panel size, active/available/region/COI/minimum expertise, slot capacity and expert daily capacity from the run parameters, and existing published bookings. Then publish all drafts in one UPDATE; the partial unique index remains the final guard and a violation maps to 409 EVC_EXPERT_DOUBLE_BOOKED. Requests and the run become PUBLISHED; one `evc.assignment_published` per assignment is appended to the application aggregate (case timeline). Any failure rolls back everything.
8. APIs: `POST /api/evc/schedule:propose` (201) and `POST /api/evc/schedule:publish` (200), both through `idempotent_response` with an optional Idempotency-Key. Responses carry the selector label, SIMULATED/DEMO_ASSUMPTION status and assumption code EVC_SCHEDULING_POLICY_UNCONFIRMED.
9. Lifecycle: QUEUED → PROPOSED → PUBLISHED → DONE. Workflow cancellation of a QUEUED or PROPOSED request now withdraws its unpublished drafts (they reserve nothing); a published assignment still fails closed with EVC_SCHEDULE_CANCELLATION_REQUIRED until an unpublication lifecycle exists.
10. Merge repair: the platform policy compares RO regions exactly, which refused a Southern RO on SOUTHERN experts before the EVC case-insensitive check, and the queue's listing check stated no region for a region-scoped kind. EVC now hands the policy the principal's own spelling once regions match case-insensitively; RO users without a region are refused by the platform with 401 (tests updated).

## EvcPort.status contract for complete_evc

No port change. `port(EvcPort).status(session, application_id)` returns the latest request status; it is `"PUBLISHED"` exactly when that request's run has been published (published assignment with a date/part and panel). The workflow already injects this as `GuardFacts.evc_request_status` when the case is in EVC. A guard for complete_evc should require `evc_request_status == "PUBLISHED"`; the existing `evc_request_open` accepts QUEUED/PROPOSED/PUBLISHED. Note for that change: workflow/acceptance tests and the 600-case replay that call complete_evc without scheduling would then need a propose+publish step (or a fake EvcPort status).

## Benchmark — `python generator/cases/evc_benchmark.py`

Seeded DEMO pool from seed_evc_demo.demo_rows (30 experts, 9 DEMO regions, 60 days, 3 COIs); 361 synthetic requests (seed 26262, 0–2 arrivals per region per day for 40 days, 35% from the COI institution where one exists), 7-day window, panel size 3, slot capacity 4, one visit per expert per day. Pure, no database; runtime measured on the development laptop, single worker.

| max_lateness_days | algorithm | scheduled / 361 | total lateness (days) | late visits | start offset (days) | runtime |
|---|---|---|---|---|---|---|
| 0 | EDF | 272 | 0 | 0 | 1229 | 3.7 s |
| 0 | CP-SAT | **273** | 0 | 0 | 557 | 25.4 s |
| 7 | EDF | 299 | 673 | 135 | 2146 | 7.6 s |
| 7 | CP-SAT | 299 | **191** | 45 | 1134 | 31.2 s |

CP-SAT status FEASIBLE (deterministic limit reached), no repair rounds, no EDF fallback. Every unscheduled request is CAPACITY_EXHAUSTED: the scenario is deliberately overloaded (~1 arrival per region-day against ~1 panel per region-day). Two consecutive runs produced identical outputs apart from runtime. The test suite uses a 14-day, 4-region slice of the same generator plus a hand-built case where EDF schedules 1 of 2 and CP-SAT 2 of 2.

## Source and integration limits

The SIMULATED selector stand-in is still not the official authorised selector and P3 identity lookup is still absent. No unpublication, rescheduling of published visits, expert notification or visit-outcome recording exists. Slot capacity, expert daily capacity, AM/PM parts and lateness allowance are DEMO ASSUMPTIONs. Large national runs take tens of seconds; regional runs are the intended use.
