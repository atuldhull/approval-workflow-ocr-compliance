## Explicit integration limit

P3 owns user/role master data, but publishes no lookup port or read-only view here. Registration accepts an opaque externally supplied user_ref; it does not certify that the user exists or has an expert role. Authoritative validation needs a future P3 interface. Optional personal data is not an identity authority. Do not invent legal region/COI rules or bypass ownership to query P3 tables.

## API and policy details

- Expert registration accepts user_ref, region, coded expertise_tags, active and optional personal_details (name/phone/email). Only PersonalDataPort sees the personal object. Expert responses/events store personal_ref only and mark identity_status=P3_USER_REF_UNVERIFIED. Duplicate user_ref returns Conflict 409 without personal/ledger effects; the deterministic expert UUID is derived from user_ref.
- Regions are canonical uppercase tokens; comparisons with existing request/RO regions are case-insensitive. No mapping of DEMO_REGION codes to official RO geography is invented.
- Bulk availability uses `{items: [{date, slot_part, available}]}` (1–732 distinct date/part keys). Dates are ISO calendar dates, parts AM/PM; updates are sorted and only changed entries enter the event. Identical requests are no-ops. This changes declared availability, not an existing schedule; it neither cancels nor silently rewrites assignments.
- COI accepts expert_id, institution_ref, source and matching reason_code. Repeated identical entries are no-ops. A missing stable institution ID returns 404 through the existing FK constraint, without querying another module's internal table.
- GET /api/evc/experts supports region, available_on, optional slot_part and offset/limit. It is a directory, not institution-specific eligibility: COIs need an EVC request context and are applied in eligible_experts. available_on requires active=true, a true availability row and an unreserved slot part. Unknown availability is unavailable. Without the date filter, inactive entries remain visible with their active flag.
- Both proposed and published assignment memberships exclude an expert for that date/part, conservatively; the DB publication uniqueness protection is unchanged. Eligibility snapshots require the request's pinned key, not the current default. Future schedulers must recheck reservations in their publication transaction; a snapshot is not itself a reservation.
- Existing checksum rejection remains intact. The added r1 policy uses fresh disposable demo databases for verification, as with earlier approved r1 updates. No old cache/pin is rewritten. No P2 files are changed.

## Verification environment and focused results

The Docker-focused run was interrupted by repeated WSL networking failures. Both Docker restart and the broader WSL shutdown were explicitly authorized; the initial automatic rejection of the broader shutdown was resolved by the user's separate approval. WSL still reported failure to configure its NAT network, so verification moved to an isolated native PostgreSQL 16.15 cluster bound to 127.0.0.1:55436, under a dedicated temporary directory. No Windows service, repository database setting or P2/P3 runtime configuration was changed.

The existing backend/alembic.ini uses space-separated version_locations; the original checkout's user path contains a space. Native Alembic therefore silently found no revisions there, causing undefined-table setup failures. This is a pre-existing P3 configuration follow-up, not fixed in this task. A temporary source copy at a space-free path is used instead. SHA-256 comparison of 168 source/data files found zero differences. The local Python 3.12 environment uses the pinned FastAPI 0.115.6, Pydantic 2.10.3, SQLAlchemy 2.0.36, pytest 8.3.4 and psycopg 3.2.3 versions.

The initial proper-path focused run passed 92 tests and exposed five incomplete test doubles (missing required protocol methods) plus an order-dependent existing migration test after pool data was left behind. Complete ledger/ruleset test doubles and EVC-only fixture cleanup fixed the test harness. The corrected run of all 40 new pure/API cases plus the subsequent EVC model/migration comparison passed **41 tests**, with one pre-existing Starlette/AnyIO deprecation warning (169.04 seconds). Production behavior did not need to change in response to those harness failures.

`python scripts/check_contracts.py --write` passed and refreshed the approved OpenAPI in the actual checkout. The final complete pytest and contract/migration results are recorded below and supersede all interrupted runs.

The first full native run exposed the local cluster's default Asia/Calcutta session timezone: existing committee POST/GET equality tests compared UTC `Z` output against `+05:30` output for the same instant. A separate disposable-database reproduction confirmed this exact mismatch. The temporary PostgreSQL cluster was aligned to the project's UTC Docker baseline (no repository or user OS timezone change); the reproduced committee test then passed. The interrupted full run is not counted as a pass. A fresh complete run is now executing against UTC.

The subsequent UTC full run caught a genuine concurrent-registration bug after 119 passes: PostgreSQL could report expert_pkey under two simultaneous inserts because ON CONFLICT targeted only user_ref. Registration now uses untargeted ON CONFLICT DO NOTHING, covering both existing unique keys without overwriting either row; a losing request returns the existing coded Conflict 409 and performs no personal/ledger effects. The concurrent registration/bulk retry test now runs three deterministic attempts (42 new cases total). The stopped 119-pass run is not represented as a full pass. Targeted concurrency and a fresh full run follow this fix.
