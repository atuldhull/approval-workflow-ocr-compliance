# EVC scheduling decisions (3.7) — decided 28 October 2026

Builds on plans 3.5 (EDF baseline) and 3.6 (CP-SAT and publication). The 3.6 open questions were delegated by P1 with "accept the best option"; this records the choices and what changed. The 3.5/3.6 design stays: one immutable `SchedulingProblem`, the SIMULATED authorised selector (stand-in) forms every panel, `evaluate_schedule`/`compare_plans` score both planners, and publication rechecks with the same evaluator. Assumption IDs SCHED-DEC-001…007 are in ../ASSUMPTIONS.md.

## Decisions

1. **Expert daily cap — reinstated, configurable (DEMO ASSUMPTION).** `expert_pool.scheduler.expert_daily_cap` in the pinned ruleset, r1 = 1 visit per expert per date (optional key, default 1). It travels as `SchedulingProblem.expert_daily_cap` (part of the input fingerprint). `selector_at` marks an expert who already has the cap's number of visits on a date as reserved for every part of that date, so EDF, CP-SAT witnesses and panel materialisation all go through the unchanged `eligible_experts`/`select_panel`. CP-SAT adds a per-expert, per-date constraint over its witness variables. `evaluate_schedule` counts visits beyond the cap as `EXPERT_DAILY_CAP` (only visits added by the plan; earlier commitments are the baseline), so the publication recheck enforces it too: a cap breach alone is 409 EVC_EXPERT_DAILY_CAP_EXCEEDED, mixed with other violations 409 EVC_PUBLISH_RECHECK_FAILED. A run takes the strictest cap among its requests' pinned rulesets; the value is stored as `expert_daily_cap` in the run parameters and returned by propose.
2. **Per-request explanations — additive.** `explanations.explain_unscheduled(problem, plan)` derives one code per unscheduled request from the same problem types, judged against the final plan: NO_AVAILABILITY → PANEL_INCOMPLETE → COI_ONLY → CAPACITY_EXHAUSTED (full slots, or expert time taken by other visits) → EXPERT_DAILY_CAP, with NO_FEASIBLE_SLOT as the fallback (no slot in the window, or no specific cause). `reason_code` stays NO_FEASIBLE_SLOT for every unscheduled request; `explanation_code` is new in the propose response only. No event payload changed.
3. **Slots.** `slot_capacity` on propose stays the demo path: it creates only missing AM/PM date/parts and never changes existing slot rows. Documented in the README, the route description and SCHED-DEC-003; no separate endpoint.
4. **CP-SAT candidate window.** `expert_pool.scheduler.cpsat_candidate_slots`, r1 = 12 (optional key, default 12), passed to `CpSatParameters.max_candidate_slots`. Reported as `cpsat_candidate_slots` in run parameters and `solver.candidate_slots` in the response. A run takes the widest value among its requests' rulesets.
5. **Re-planning.** `POST /api/evc/schedule:discard` {run_id}, bureau only through the existing `evc.schedule.publish` permission (policy.py unchanged). A PROPOSED run's drafts are deleted, their requests return to QUEUED and the run becomes DISCARDED; published or already discarded runs are 409 EVC_RUN_NOT_DISCARDABLE, an unknown run 404. No existing event fits a withdrawal, so evc.schedule_discarded.v1 (run aggregate) is added in its own `contract(events)` commit; see ../contract_requests/2026-10-28_evc_discard.md. Optional Idempotency-Key.
6. **Regions.** Case-insensitive matching stays. An RO naming another region is 403 SCHEDULE_REGION_FORBIDDEN (unchanged). A bureau region that no expert or EVC request names is 422 SCHEDULE_REGION_UNKNOWN; there is no official region taxonomy, so "known" means present in the EVC data.
7. **evc.assignment_published.v1** accepted by P1 as proposed, unchanged.

The regenerated OpenAPI (discard route, `expert_daily_cap`, `explanation_code`, `solver.candidate_slots`, descriptions) is committed on its own as `contract(openapi)` and needs three-way approval.

## Benchmark with the daily cap — `python generator/cases/evc_benchmark.py`

Same seeded DEMO pool and synthetic queue as 3.6 (361 requests, 30 experts in 9 DEMO regions, 3 COIs, panel size 3, AM/PM capacity 4 panels, 7-day due window), now with the pinned cap of 1 visit per expert per date and 12 candidate slots. Pure, no database; single worker on the development laptop.

| scenario | algorithm | scheduled / 361 | late | total lateness | max lateness | total waiting (days) | violations | runtime |
|---|---|---|---|---|---|---|---|---|
| late planning off (47 days) | EDF | 272 | 0 | 0 | 0 | 1229 | 0 | 17.1 s |
| late planning off (47 days) | CP-SAT | 272 | 0 | 0 | 0 | **1227** | 0 | 59.7 s |
| late planning on (54 days) | EDF | 299 | 135 | 1026 | 20 | 2499 | 0 | 23.5 s |
| late planning on (54 days) | CP-SAT | 299 | **34** | **285** | 20 | **1316** | 0 | 64.2 s |

All 89 (late off) and 62 (late on) unscheduled requests explain as EXPERT_DAILY_CAP for both planners. CP-SAT status FEASIBLE (deterministic limit reached) in both scenarios, no repair rounds, no EDF fallback; 3516 and 4440 candidate (request, slot) pairs.

Reading: with one visit per expert per day the DEMO pool is now the bottleneck (3 or 4 experts per region form at most one panel per region per day), so neither planner can place every request: 75% within the window, 83% with late planning. CP-SAT cannot raise the count inside the window here, but with late planning it cuts late visits from 135 to 34, total lateness by 72% and total waiting by 47% at the same count. Without the cap (3.6 figures) EDF already placed 360–361 of 361. The cap is a DEMO ASSUMPTION; raising `expert_daily_cap` to 2 restores the 3.6 behaviour.
