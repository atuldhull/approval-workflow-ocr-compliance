## API handoff

All paths use `/api`. POST `/cases/{id}/committees` accepts `{type, members:[{user_ref,role}]}` and requires its caller in the list. POST `/committees/{id}/tasks` accepts `{title_key,assignee_user_ref}`; POST `/tasks/{id}/observations` accepts `{body}`; POST `/committees/{id}/reports` accepts `{content,parent_version?}`. Authors/timestamps/IDs/version numbers are server-attributed. All POSTs return 201. GET `/committees/{id}` returns members, tasks/observation refs and report_count; GET `/committees/{id}/reports` returns all versions in ascending order with explicit hash-only diff metadata. Report UPDATE/DELETE endpoints do not exist, and database triggers reject those operations.

Events are wf.committee_formed.v1, wf.task_assigned.v1, wf.observation_added.v1 and wf.report_version_added.v1 (event_type excludes the file version suffix). All appear on the case timeline through the real ledger. Storage is wf.committee, wf.committee_member, wf.task, wf.observation and wf.report_version. Protected note references/hashes remain stable in append-only reports; no personal display names or raw prose are stored in these wf tables or emitted in events.

Operational codes/formation/read permissions are DEMO ASSUMPTIONS recorded in ASSUMPTIONS.md. No APH composition/quorum rule is asserted.
