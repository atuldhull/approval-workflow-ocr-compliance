# Idempotent P1 POST endpoints plan

Read platform/idempotency.py (`idempotency_key`, `idempotent_response`, `run_idempotent`, IdempotencyStore), docs/IDEMPOTENCY.md, P2's compliance/deadline/document endpoints and the EVC schedule endpoints that already use it, test_idempotency.py, and every P1 POST handler.

## Implementation

Every P1 POST now runs its unit of work through `idempotent_response` with the optional `Idempotency-Key` dependency, exactly the platform semantics: the key row is claimed and the response stored inside the command's own transaction; a retry with the same key and body replays the stored status/body with `Idempotent-Replayed: true`; the same key with a different body (path parameters included in the fingerprint) is 422; a request blocked behind an uncommitted holder of the key gets 409 after the lock timeout. A failed command rolls back its claim, so the same key can be retried once the cause is fixed. Keys are scoped per user, method and route template.

| Group | Endpoints |
|---|---|
| Case actions | `POST /api/cases/{id}/actions` |
| Intake | `POST /api/applications`, `/api/applications/{id}/items`, `/api/applications/{id}/submit` |
| Committees | `POST /api/cases/{id}/committees`, `/api/committees/{id}/tasks`, `/api/tasks/{id}/observations`, `/api/committees/{id}/reports` |
| Deficiency | `POST /api/cases/{id}/deficiencies/{deficiency_id}/review` (compliance submission is the `submit_compliance` case action) |
| EVC pool | `POST /api/evc/experts`, `/api/evc/experts/{id}/availability`, `/api/evc/coi` (propose/publish already did) |

`expected_version` optimistic concurrency is unchanged: a new key with a consumed version is still 409 VERSION_CONFLICT; only the identical retry is answered from the store. The case-action Idempotency-Key header now uses the platform format (8–128 of `A-Za-z0-9_-:.`) instead of the earlier 1–200 "reserved" header. Report bodies are fingerprinted with `exclude_unset` so an omitted `parent_version` (append to head) differs from an explicit null. Error bodies such as intake's MANDATORY_ITEMS_MISSING are unchanged and never stored.

## Tests

`backend/tests/test_p1_idempotency.py`: per group, first call runs, retry replays an equal body with the header, a changed body is 422, and exactly one ledger event exists; blocked submissions and refused actions leave no stored response and succeed with the same key later; a consumed expected_version under a new key is 409; a case action behind a held key gets 409 (lock timeout lowered to 200 ms in the test). `test_workflow_case_api.py` now expects the replay instead of 409 for an identical keyed retry.
